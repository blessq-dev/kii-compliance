# Прототип: автоматизированная оценка соответствия значимых объектов КИИ

Прототип к магистерской ВКР (ИТМО, ФБИТ). Метод: формализованная база правил (YAML)
+ движок правил (Python), отделённый от интерфейса (Streamlit).

## Что делает

1. Пользователь вводит сферу деятельности и показатели значимости объекта.
2. Движок определяет категорию значимости по ПП РФ № 127.
3. По категории формируется базовый набор мер из приложения к приказу ФСТЭК № 239;
   пользователь отмечает реализованные меры, адаптацию набора (п. 23) и компенсирующие меры (п. 26).
4. Проверяются организационные требования к системе безопасности (приказ ФСТЭК № 235).
5. Отчёт о несоответствиях со ссылками на источник и черновик акта категорирования (ПП № 127, п. 16).

## Установка и запуск (для пользователя, Windows)

**Вариант 1 — одна программа (рекомендуется).** Скачайте `КИИ-Оценка.exe` и запустите двойным
щелчком. Python и интернет не нужны. Через 5–10 секунд откроется окно программы; чтобы завершить
работу, закройте окно. Оценки, журналы эксперимента и добавленные редакции правил сохраняются
в папку «КИИ-Оценка — данные» рядом с exe (если туда нельзя писать — в `%LOCALAPPDATA%\КИИ-Оценка`).

Если Windows покажет «Система Windows защитила ваш компьютер» — нажмите
«Подробнее» → «Выполнить в любом случае» (программа не подписана сертификатом издателя).

**Вариант 2 — из исходного кода.**

1. **Установите Python 3.11 или новее** с https://www.python.org/downloads/.
   В первом окне установщика отметьте галочку **«Add python.exe to PATH»**.
2. **Скачайте программу:** на странице репозитория нажмите зелёную кнопку
   **Code → Download ZIP** и распакуйте архив в любую папку.
3. **Запустите `run.bat`** двойным щелчком.
   - Первый запуск ставит нужные библиотеки (нужен интернет, 1–3 минуты).
   - Затем в браузере откроется программа: http://localhost:8501.
   - Чтобы завершить работу, закройте чёрное окно консоли.

**Сборка exe** (для разработчика): `pip install -r requirements-build.txt`, затем
`python build_exe.py` — результат в `dist/КИИ-Оценка.exe`. Точка входа — `launcher.py`
(запускает интерфейс в фоне и показывает его в отдельном окне).

### Как пользоваться

Оценка идёт по пяти вкладкам; сверху всегда видна сводка: категория,
заполненные показатели, закрытые меры, уровень соответствия.

1. **Объект и сфера** — наименование, сфера деятельности, признаки ГИС/ИСПДн (п. 24 приказа № 239).
   Здесь же: сохранение оценки в файл, **перечень объектов** субъекта (сохранить, открыть, удалить),
   демонстрационные примеры.
2. **Показатели значимости** — заполните только применимые. Под каждым полем — справочные
   значения из ПП № 127 (подсвечивается диапазон, в который попало значение), пояснение
   для граничных значений, проверка ввода (ошибки блокируют отчёт). Показатели 8, 10, 10(1)–10(7),
   13, 13(1) и 14 применяются только к субъектам (объектам) определённого вида — условие нужно
   подтвердить отметкой, иначе заполненный показатель считается ошибкой ввода.
3. **Меры защиты** — отметьте реализованные меры вручную или загрузите их перечень из файла
   TXT/CSV (коды вида «УПД.3»); поиск и фильтр «только нереализованные».
   В **карточке меры** — статусы «не применяется» (адаптация, п. 23) и «компенсирована» (п. 26)
   с обязательным обоснованием, «чем реализована» и плановый срок для нереализованных.
4. **Система безопасности** — чек-лист из 48 требований приказа № 235; 10 условных требований
   (филиалы, привлекаемые организации, дочерние общества, встроенные СЗИ и др.) можно отметить
   «не применимо».
5. **Отчёт** — категория с обоснованием, диаграммы, несоответствия, адаптация, требования № 235;
   выгрузка: **отчёт (DOCX)**, **черновик акта категорирования (DOCX)**, Markdown, JSON.

Для знакомства: вкладка 1 → «Демонстрация» → выберите объект → «Загрузить пример».

### Эксперимент «вручную vs система» (для ВКР)

1. Слева включите **«Режим эксперимента»**.
2. Укажите участника, выберите тестовый объект, скачайте **карточку объекта** (исходные данные
   без ответов) и выдайте её участнику.
3. **Через систему:** «Начать оценку объекта через систему» → участник вводит данные по карточке
   → «Сформировать отчёт». Время и результат записываются в `data/results/experiment_system.csv`
   и сразу сравниваются с эталоном.
4. **Вручную:** участник оценивает объект по документам, результат вносится в форму
   «Внести результат ручной оценки» → `data/results/experiment_manual.csv`.
5. `python experiment.py` — сводка: точность категорирования, recall, precision, среднее время
   и сокращение времени оценки.

## Запуск для разработчика

```
pip install -r requirements.txt
streamlit run app.py        # интерфейс
pytest                      # тесты
python experiment.py        # эксперимент: метрики на тестовом наборе и журналы участников
```

Тесты автоматически запускаются в GitHub Actions при каждом push (`.github/workflows/tests.yml`).

## Метрики для ВКР

- **Время оценки** — вручную и через систему (журналы эксперимента).
- **Точность категорирования** — доля оценок с категорией, совпавшей с эталоном.
- **Полнота (recall)** — доля эталонных несоответствий, найденных участником.
- **Точность (precision)** и **доля ложных несоответствий** (1 − precision).

## Принятые решения

- **Нормативка применяется буквально.** Места, где текст документов внутренне противоречив
  (исходные редакции: ПП № 127 — п. 5, 9а, 14, приказ № 239 — мера ДНС.5), перенесены дословно,
  а движок выводит по ним замечания в отчёт. В действующих редакциях эти дефекты устранены;
  верификатор нашёл новые замечания (ПП № 127 — нет порога значимости у пп. 5б, 10, 10(1), 10(2);
  приказ № 239 — направление п. 22 «т» без мер в приложении). Подробно — в `notes/`.
- **Редакции:** в базе по две редакции каждого документа. Действующие: ПП № 127 — ред. от 07.11.2025;
  приказ № 239 — ред. от 28.08.2024; приказ № 235 — ред. от 20.04.2023; 187-ФЗ — ред. от 07.04.2025.
  Исходные: ПП № 127 (2018), приказ № 239 (ред. 2018), приказ № 235 (ред. 2019), 187-ФЗ (2017).
  Промежуточных редакций нет: их текстов в `docs/` нет. Перечень редакций выводится в каждом отчёте.
- **Новая редакция документа = новый пакет правил**, код не меняется (см. ниже).
- **Приказ № 235** относится к системе безопасности субъекта (п. 2) в отношении всех его
  значимых объектов (п. 3) и проверяется как организационный чек-лист.
- **Сфера вне 187-ФЗ** → объект не подлежит категорированию (187-ФЗ, ст. 2, п. 8; ПП № 127, Правила, п. 2).
- **Пустой показатель** = неприменим к объекту (ПП № 127, Правила, п. 6, абз. 3).
- **Уровень соответствия** = (реализованные + компенсированные) / (обязательные − неприменимые).
  Если все меры исключены при адаптации, уровень не определён (и выводится замечание).
- **Проверки адаптации** — только формальные: обоснование написано словами; компенсирующая мера
  не совпадает с компенсируемой; указанная кодом компенсирующая мера должна быть реализована;
  исключённая мера «.0» группы (правила и процедуры) при оставшихся мерах группы — замечание. Достаточность
  компенсирующих мер оценивается при приёмочных испытаниях (п. 26 приказа № 239), не системой.
- **Незаполненные показатели** перечисляются в обосновании категории как неприменимые; если
  не заполнен ни один показатель — предупреждение о возможном занижении категории.
- **ГИС/ИСПДн** (п. 24 приказа № 239) — только предупреждение: требования к защите ГИС и ИСПДн
  в `docs/` отсутствуют и в базу правил не включены.
- **Акт категорирования** — черновик по составу сведений п. 16 Правил; результаты анализа
  угроз заполняет комиссия.

## Новая редакция документа

1. Положите текст новой редакции в `docs/`, обновите выжимку в `notes/`.
2. Создайте пакет `rules/<документ>/<дата>.yaml`: скопируйте прежний пакет, в паспорте
   (раздел `document`) укажите редакцию и дату `effective_from`, с которой она применяется,
   внесите изменения в правила.
3. Пакет можно добавить и через интерфейс: вкладка 1 → «База правил: редакции и обновления».
   Пакет проверяется автоматически; пакет с ошибками не добавляется.
4. Оценки на даты до `effective_from` выполняются по прежней редакции, после — по новой
   (дата оценки выбирается в боковой панели).
5. В том же разделе интерфейса — сравнение редакций: что изменилось в правилах и как это
   повлияет на объекты из перечня (категория, новые обязательные меры, новые несоответствия).

Проверка пакета (`engine/verification.py`) находит ошибки структуры (повтор кода, правило без
источника, несуществующее условие) и дефекты самого текста документа: пересечения и разрывы
диапазонов, нарушение монотонности шкалы, непокрытый «тяжёлый» край шкалы, отсутствие порога
значимости, нарушение вложенности наборов мер, направления п. 22 приказа № 239 без группы мер. Сценарий «вышла новая редакция» проверяется тестами `tests/test_packages.py`.
